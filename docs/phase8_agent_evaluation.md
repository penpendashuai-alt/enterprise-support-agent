## 2. 运行与审阅契约

`scripts/evaluate_agent.py` 默认只校验场景和来源，不调用付费 API。真实模式必须显式传入 `--paid --budget 30` 和未使用的输出目录。Chat 单次最多输出 1800 token、温度 0、不自动重试；Embedding 的既有重试逐物理调用记账。全阶段最多 1200 次物理调用，至少预留 1 元。未知用量记 null 并阻断后续调用，不能填零。

服务实验使用真实 loopback HTTP 和 Uvicorn，服务端执行真实 Router、聊天模型、Embedding、Qdrant、Checkpoint 与业务存储。每次建立独立 PostgreSQL 数据库、合成用户、会话及 Redis namespace。三个应用数据库池各上限 1；评测器另有上限 1 的审计池。单 worker、串行低速，主质量实验关闭检索缓存，准入控制开启。服务状态和设备查询仍是固定 Mock；本地 DEMO 工单不是 Jira/ServiceNow 写入。声明式 user_id 的归属检查不是完整身份认证。

审批驱动从真实草稿提取 ID、版本与完整字段，再发 edit/approve/cancel；没有生成预期草稿就记录失败，不自动纠正模型。重复批准沿用同一草稿版本，数据库必须只有一张工单。SSE 样本保存事件、最终 message 与 DONE 检查；这里不报告 TTFT，客户端收完响应后统一解析。

每个任务逐轮落盘，回答编号校验前文本通过评测钩子记录；非知识回答的可见模型原文保存在物理调用账本，任务中的 `model_calls` 列出关联 ID（该字段实际包含 Chat 和 Embedding）。不存隐藏思维链。普通测试不调用付费服务，评测钩子不接入产品请求。

语义审阅由参与设计和实现的开发助手完成，**不是独立人工盲评**。审阅绑定原始记录 SHA-256，记录时间、规则、逐行摘录、理由、必要要点和不确定项。行内包含多个事实时，任一不支持的事实使该行不支持；分段只整理已经作出的审阅判断，不用关键词判断事实。编号出现在线首、列表标题时，按相邻段落核对引用范围；复核发现三条记录漏归属段落引用，已补入引用映射并保留此前审阅，最终引用指标以 `final-v2/` 为准。常识解释单列，不用整部知识库为未提供给模型的条款事后辩护。

汇总使用预定任务数作任务分母；失败、未执行、待审不被删除。需要路由的标注轮次才进入意图分母；必需工具、实际调用合法性、参数与多余调用分列。完整性、错误拒答、含无依据陈述比例和引用支持性同时报告，零分母为 null。P95 使用 `floor((n-1)*0.95)`，不拼接历史阶段的不同算法。

## 3. 开发集发现与候选

Phase 7 基线为 Git `6015d4e5ea9f24533222703e51bfed1eef7947d2`，开发前工作区干净，Git archive 的本地可恢复副本和公开逐文件哈希已保存。首次正式开发基线执行到第 31 个任务时记录了 `PermissionError`；该任务仅完成三轮，后续五个任务未运行。原始结果、费用与未执行分母保留，不能用新结果替换首次失败。

Windows 文件读写重叠时原子替换可能短暂被拒绝。评测器增加有界替换重试，测试模拟首次替换失败后恢复；原始日志未保留 traceback，因此首次错误的文件锁归因是推断。修复后的 `dev-baseline-v2` 是另一次完整开发实验，与首轮中断结果分别汇总。它不是隐式重试，也没有重放原审批会话。

两项候选改动仅涉及提示词：

1. `HANDLER_PROMPT` 与证据提示要求保留适用系统、协议、授权条件，回答有据部分，说明无据部分，避免从“一般建议”补写具体步骤或把模拟字段称作用户实际配置。
2. 准确说明回答节点工具只读、整个 Agent 可以通过草稿与结构化确认创建本地 DEMO。原提示词“你没有创建、提交或修改工单的能力”会被回答直接复述，混淆节点与产品能力。

没有改变 Dense20/v2、0.65 门槛、索引快照、缓存键、审批、实体状态或数据库代码；因此不需要为检索结果更新缓存版本。候选回答提示词摘要已更新并重新评测。两项改动作为一个候选比较，没有声称单独归因每项收益。

开发集复核结果：修复后的基线确认成功 29/36，候选 30/36；两组结构断言均为 36/36。候选修正部分设备模拟字段和能力边界陈述，但有普通概念回答退步，不能把小样本净增一个任务称为稳定提升。原始配对表保留每个场景变化。

数据质量限制也属于失败分析：`priority_policy-2` 标签额外要求 SLA，`priority_policy-3` 标签额外要求影响范围和审批修改，`privacy-1` 复合标签额外要求最小收集原则，均超出对应问题的直接询问范围。首次冻结后未改标签或为候选放宽标准；两组按原契约计遗漏并归为 `annotation_scope`，不将这三项作为模型改进依据。后续新版本应先修正标签再做新实验。

## 4. 组件与历史失败

原始问题检索直接调用检索器，不经过 Router。固定证据生成重放记录中的 evidence，不重新检索、不提供工具结果；原始查询、候选与最终证据均保存。包含设备号的问题可能诱发模型声称查过设备，但组件根本没有执行工具；这种编造仍算失败，不能包装成真实业务调用。

P1 短问在固定证据中只取得优先级边界块，两组仍缺少定义。提示词不能补回未提供的条款，未实施邻块补充。冲突回答保留 A/B 规则及管理员核对，不允许自行创造更严格的临时制度。真实注入问句可能被 Router 改写为审批流程，未摄入恶意分块时不能据此宣称抗文档注入。

原始短问检索中，P1 定义分块分数为 0.61774945，低于 0.65；边界分块为 0.6768688 并入选。主因是证据筛选，不是完全没召回文档。5 个原始问题的带来源要点覆盖为候选 7/7、最终证据 6/7。固定生成的两组都曾在没有工具的环境下编造“设备查无记录”；不能用实际模拟库碰巧存在或不存在该设备替它辩护。历史真实 Agent 回归两组均为 5/6，残留失败为 P1 定义缺失。

受控恶意证据从已记录候选中追加到 evidence，单独标记输入变换和源记录摘要，验证生成边界；不计入真实端到端检索成功。来源编号替换使用确定性无效编号输入验证，记录模型前文本与替换后模板，不声称此次真实模型自然触发过该错误。

两组都识别了追加的恶意指令并拒绝照做；该文本明确带攻击样例标签，且生成组件未绑定业务工具，不能外推隐蔽文档攻击或完整生产系统的鲁棒性。基线仍出现笼统否认创建能力，候选能力说明较准确。

## 5. 复现

使用现有 Python 环境，从仓库根目录执行。先配置本地 `.env` 与 PostgreSQL 连接文件，密钥和个人云地址不进入参数、报告或 Git。以下付费命令是本阶段已授权实验的复现方式，未来重新执行需要另行核算余额和预算；已有输出目录不会被覆盖。

```powershell
# 默认离线校验
.\venv\Scripts\python.exe scripts/evaluate_agent.py
.\venv\Scripts\pytest.exe tests/evaluation -q

# 独立真实服务实验
.\venv\Scripts\python.exe scripts/evaluate_agent.py --paid --budget 30 --variant candidate --output evaluation/phase8/runs/new-dev

# 按已冻结顺序执行留出对照
.\venv\Scripts\python.exe scripts/run_phase8_campaign.py --paid --budget 30 --freeze evaluation/phase8/candidate-freeze.json --output evaluation/phase8/new-heldout

# 导入逐条审阅并纯离线汇总；reviews 文件是 Review 数组
.\venv\Scripts\python.exe scripts/summarize_phase8.py --runs evaluation/phase8/runs/dev-candidate --reviews evaluation/phase8/runs/dev-candidate/reviews.v2.json --output evaluation/phase8/rebuilt-dev.json

# 重建最终全套报告、配对、补充草稿审计和成本；不访问模型或数据库
.\venv\Scripts\python.exe scripts/rebuild_phase8.py --output evaluation/phase8/rebuilt-final
```

每个原始运行目录自动产生 `reviews.pending.json`。复制并填写全部必要要点、逐条陈述与理由后，通过 `--reviews` 导入；原始记录摘要不匹配、遗漏要点、重复审阅或虚构摘录会被拒绝。`--export-review` 可导出完整请求、回答与证据包。离线汇总可组合不重叠的同方案分片，但会核对源代码、数据、提示词、配置与索引相同；同题的两个独立实验不能混成更多成功样本。

组件入口使用 `--layer retrieval` 或 `--layer fixed_evidence --evidence <已记录检索目录>`；只接受单轮用户问题，避免把多轮审批假装成组件生成。`scripts/compare_phase8.py` 比较两份离线摘要中的相同 case_id。调用账本只能串行使用，未实现跨进程并发预算锁，不能并行启动多个付费评测。

开发集中的故障子集为每组 3 个任务，全部明确报告检索不可用、没有冒充无资料或成功检索；`healthy` 与 `faults` 分开汇总。每组正式实验为 60 个任务、93 次 HTTP 请求，两组不是 120 个独立场景。首次中断基线保留 25/36 的确认成功下界、1 项评测器错误和 5 项未执行，不加入完整开发对照的成功数。原始试运行、组件、历史回归及缓存子集均不扩充正式样本分母。

留出的两个打印机任务选择 `general_question` 后正确检索并回答，但冻结标签只允许 `troubleshooting`，因此两组都记结构失败，归因包含标签合理路径过窄。VPN 691 仍出现从模拟正常状态推导故障倾向，或把“不能直接归为网络问题”写成排除网络因素。仓库私钥问答两组都将来源未解释的技术原因写成有引用的结论；候选末尾承认无依据也不能抵消前文越界。

**补充草稿语义审计**：原冻结集合把审批任务设为结构审阅，未逐项约束自然语言草稿。留出后补审发现“请安排人工检查”被写成“已尝试安排人工检查”：基线 1/3、候选 2/3 维修草稿存在此问题；缓存子集另有 1 条。开发集的 12 个流程任务逐项补审均未发现该偏差。共补审 43 个历史/正式/缓存任务记录，证据见 [draft-audit](../evaluation/phase8/draft-audit.json)。数据库与幂等正确不能证明草稿事实忠实，因此正式完整任务结论使用上表补充审计行，冻结 20/24 只表示原契约通过，不能当作完整语义成功率。

补充审计是留出后的分析，不是预注册指标；没有据此修改运行时代码、重跑留出或声称显著性。草稿生成提示词未在本轮修改，温度 0 也不保证相同输出，不能把两组草稿差异直接归因于本轮回答提示词。当前保留两项局部改动，同时明确：**没有证明整体质量提升，仍有可复现失败**。

所有正式任务都完成了规定审阅；另对原先仅做结构审阅的 15 个任务/方案补审草稿。每方案 15 个审批/归属任务的协议与数据库断言通过，包括未批准不创建、取消不写、修改后版本变化、重复批准只有一张工单及跨用户拒绝。自然语言字段的语义问题仍列为失败。

预选缓存子集：P1 冷检索写入后，同查询重放命中 Redis，evidence 完全相同，Embedding 请求与 token 均为 0；偏好删除后的新会话回答正确；重复批准仍返回同一工单。冻结流程检查为 3/3，补充草稿审计后为 2/3。该热缓存检查是检索重放，没有重复审批业务动作，也不证明端到端延迟提升。
